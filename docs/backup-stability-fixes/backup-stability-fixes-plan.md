# 备份修复 实施方案

## 1. 背景与目标
【功能名称】backup-stability-fixes
【背景】
用户反馈，系统执行备份功能时一直失败，且失败提示仅显示"Backup failed: "（无具体原因）。并且在失败后，备份面板的按钮处于持续禁用状态，必须退出设置界面重新进入，才能再次触发备份。
【目标】
1. 修复因网络超时导致的大文件备份失败问题。
2. 修复备份失败时错误信息为空白的问题。
3. 修复前端组件在备份失败后状态卡死、无法再次触发的问题。
【核心功能点】
- 在 WebDAV/S3 上传时移除或大幅延长 httpx 客户端的请求超时时间限制（设为 None 或数小时）。
- 捕获异常时，若 `str(exc)` 为空，提供回退的错误类型提示（如使用 `repr(exc)`）。
- 前端 `BackupRestorePanel.tsx` 在捕获到备份/恢复错误后，通过 `setTimeout` 定时清除 `activeBackupTask` 状态，解除按钮禁用。
【边界】
本修复仅针对备份与恢复的请求超时及前端状态管理，不涉及底层的加密、压缩逻辑修改。
【关键假设】
备份失败是因为大体积文件上传超过了现有的 `timeout=120.0` 限制，导致 `httpcore.WriteTimeout` 且其 `str()` 转化为空。

## 2. 需求分析
### 2.1 功能需求
- 支持长时间、大体积的数据流传输而不被客户端强制切断。
- 保证前端面板在任务遇到异常后能够回退到“可重试”状态。
### 2.2 非功能需求
- 代码健壮性：异常信息需更加清晰明确，避免直接抛出无法解读的空字符串。

## 3. 技术方案
### 3.1 WebDAV / S3 上传超时配置
在 `backend/backup/storage/webdav.py` 等存储实现中，将上传/下载时传入的 `timeout=120.0` 改为 `timeout=None`。因为 `httpx` 在流式传输大文件时需要无时限等待网络响应。
### 3.2 异常信息格式化
在 `backend/backup/manager.py` 的异常捕获块，修改 `message: f"Backup failed: {exc}"`。如果 `str(exc)` 为空，则采用 `repr(exc)`，例如 `Backup failed: WriteTimeout()`。
### 3.3 前端状态解锁
修改 `BackupRestorePanel.tsx` 中的 `handleTriggerBackup` 和 `handleExecuteRestore` 函数。在 `.catch(err => ...)` 代码块中，追加 `setTimeout(() => setActiveBackupTask(null), 5000)`，这样在展示错误 5 秒后，进度条会消失，按钮恢复可用。

## 4. 实施计划
| 任务 | 描述 | 优先级 | 预估复杂度 | 依赖 |
|------|------|--------|-----------|------|
| 1 | 修改前端 `BackupRestorePanel.tsx` 错误状态重置 | P0 | S | 无 |
| 2 | 修改 `webdav.py` 上传超时时间为 None | P0 | S | 无 |
| 3 | 优化 `manager.py` 的报错字符串输出格式 | P1 | S | 无 |

## 5. 风险与应对
| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| 取消网络超时可能导致请求无限挂起 | 任务卡住 | 低 | 用户仍可在前端手动刷新；后端备份是独立 task，进程退出后即可销毁 |

## 6. 验收标准
- [ ] 备份大体积环境时不因 120 秒超时而中断。
- [ ] 发生备份错误时，前端面板提示明确的错误类型（如 Timeout）。
- [ ] 失败 5 秒后，备份按钮自动恢复为可点击状态，无需退出重新进入设置。
